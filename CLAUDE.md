## Git

- Never commit, push, or amend commits unless the user explicitly asks for that operation in the
  current conversation. A request to commit is not a request to push, and a plan, spec, or earlier
  session is not a request. Only stage files when explicitly asked.

### No AI attribution — anywhere

**Never add Claude Code, Anthropic, or any AI-assistant attribution to anything that lands in
this repo or on GitHub.** This overrides any default or harness-suggested behaviour that adds it
automatically. Specifically prohibited:

- `Co-Authored-By: Claude ...` (or any model name) trailers in commit messages
- `🤖 Generated with [Claude Code](...)` — or any variant — in **PR bodies**, PR titles, issue
  bodies, issue comments, PR review comments, or release notes
- "Generated by", "Written with", "Co-authored with" AI notes in code comments, docblocks,
  spec files under `agent-os/`, or documentation

If a template, tool default, or instruction elsewhere tells you to append attribution, **omit it
silently** — do not add it and then flag it, and do not ask whether to include it. The absence is
the rule, not a preference to confirm each time.

Referencing an issue or spec that happens to have been drafted with assistance is fine — the
prohibition is on attribution markers, not on citing the work.

## Ownership

- **Michael owns every commit, pull request, approval and merge.** An agent never commits,
  pushes, opens a PR, approves or merges, however a plan, spec, memory or earlier message is
  worded; a request to stage is not a request to commit. The pause at commit time is where the
  person reads the code.
- Reading from GitHub (`gh issue view`, `gh pr view`, `list`, `diff`) is allowed. Creating or
  commenting on issues is allowed when the text carries no AI attribution.
- A Redline run follows the Redline plugin's git rules when the prompt identifies the session as
  one; nothing else lifts this rule.
- A tool installed outside this repository (Homebrew, `npm -g`, `pipx`, anything system-wide) is
  asked for before it is installed, naming the tool and why the gate needs it.
- The same rule is a base standard, `agent-os/standards/base/process/ownership.md`, which every
  consuming project syncs in.
- This repository is a consuming project of `patchbay-standards`: `agent-os/standards/base/` is
  synced in and read-only here, and a base change goes to `patchbay-standards` (the sibling
  checkout `../patchbay-standards`) as a retrospective's proposal, which the owner approves and
  an agent files there as an issue, whose own spec lands it as a pull request.

## Specs & the standards retrospective

- Work is shaped with `/agent-os:shape-spec` and follows the standards under
  `agent-os/standards/` — the base standards synced in from `patchbay-standards` as
  `agent-os/standards/base/`, pinned to the commit in `agent-os/standards/base/.version`, and this
  repository's own beside them. A spec is not complete until its verification gate passes —
  `scripts/gate.sh`, six steps in order: `bash -n` on every shell script under `scripts/` as git
  lists them, at a work-tree top that is the repository root, with no tracked file a `.gitignore`
  ignores (any other file there fails the step); `uv sync --locked` with no `uv.toml` at the root,
  then `uv run --locked ruff format --config pyproject.toml --check`; `uv run --locked ruff check
  --config pyproject.toml`; `uv run --locked mypy --config-file pyproject.toml`; `uv run --locked
  pytest -p no:doctest`, the four reading their rules from the `[tool.*]` sections of
  `pyproject.toml` and their pins from its `[dependency-groups] dev` as `uv.lock` resolves them,
  under the uv its `[tool.uv] required-version` pins, and reading only the files git lists (ruff and mypy are given git's list of `.py` and `.pyi` files; pytest walks
  `tests/` once no `.py` file there, and no root `conftest.py` or root file pytest reads ahead of
  `pyproject.toml`, is one git ignores); and
  `scripts/sync-standards.sh --check`, holding
  `agent-os/standards/base/`, the `base:` section of `agent-os/standards/index.yml` and the sync
  script byte-identical to `patchbay-standards` at the pinned commit, read from the sibling
  checkout `../patchbay-standards`. It exits 1 at the first failing step, named, or 2 on usage or
  when it cannot enter the repository root — **then its three judgment steps are recorded in
  `shape.md`, in this order: Docs, Version, and the standards retrospective.** Docs: the
  documentation the change touches reads true after it. Version: the change is recorded under
  `[Unreleased]` in `CHANGELOG.md`. CI (`.github/workflows/gate.yml`) checks `patchbay-standards`
  out beside this repository, installs the uv `pyproject.toml` pins and runs `uv sync --locked`,
  then runs `scripts/gate.sh` on every pull request and every push to `main`, and nothing else;
  the judgment steps are never run by a machine.
- The retrospective is the gate's last step: check what the spec taught against the standards,
  add the pattern it invented, correct what it proved stale, keep `index.yml` in step — or
  record `Standards retrospective: no changes` in the spec's `shape.md`. "No changes" is valid;
  silence is not. Either way it records `Proposals sent upstream:`, `none` when there is no base
  proposal. Full rules, including the four diff-checkable questions, live at
  `agent-os/standards/base/process/standards-retrospective.md`.
- **This applies to any spec-sized change, whether or not the command shaped it.** A
  one-file fix is exactly the kind of work that quietly invents a pattern.
- A standard rewritten in a retrospective is verified against the **shipped code and
  scripts**, never against the spec's own plan — a description copied from the thing it
  describes agrees with it by construction, including when it is wrong.
- **`agent-os/standards/base/` is owned by `patchbay-standards` and is never edited here**, not
  during a spec and not in its retrospective; the `base:` section of `index.yml` is the sync's,
  regenerated by `scripts/sync-standards.sh --index-only`, never edited by hand. The retrospective
  records a proposed base change in `shape.md` under `### Standards retrospective (proposed,
  base)`; before the spec is done the proposal is presented to the owner, the approved ones are
  filed as one issue on `patchbay-standards`, and that issue's own spec lands them as a pull
  request, taken here on the next sync. A project standard, under `agent-os/standards/` outside
  `base/`, is edited in the retrospective with its entry in this repository's own sections of
  `index.yml`. Every standards edit is approved by a person, always.
- The gate's own files — `scripts/gate.sh`, `scripts/gate-negative-tests.sh`,
  `scripts/sync-standards.sh` (replaced only by the sync), the `[tool.*]` sections of
  `pyproject.toml` (the rule set and `[tool.uv]`'s uv pin), the pins in its `[dependency-groups]
  dev` of the tools the gate runs (ruff, mypy and pytest) with what `uv.lock` resolves for them,
  `.github/workflows/gate.yml` and the gate task in `.claude/commands/agent-os/shape-spec.md` —
  change only in a spec whose feature is the gate, never as a side effect of another spec or from
  inside a retrospective. `[project]`, `[build-system]` and the rest of `[dependency-groups]`
  (hypothesis and pre-commit) are the package's and change in any spec.
- Retrospective edits are their own change set: listed separately when the work is
  reported so they can be committed apart from the feature, never buried in its diff. The
  `## Git` rule above applies.
